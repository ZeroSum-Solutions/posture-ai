## PR-13 — proven for strength progression

**Criterion.** Recomputing or accepting the same evidence twice must return the same proposal or a stale rejection, apply at most one advancement, and never compound from an unperformed target.

Current source covers the full behavior:

- [`decision.test.ts`](../../lib/training/progression/decision.test.ts#L737-L748) recomputes identical evidence to an identical decision without mutating the input. [`persistedProposal.test.ts`](../../lib/training/progression/persistedProposal.test.ts#L326-L333) proves the persisted proposal key is stable even when wall-clock evaluation time changes.
- The clean snapshot’s [`training_progression_proposals_test.sql`](../../work/clean-stack/posture-ai-strength-clean-release2-20260909/supabase/tests/training_progression_proposals_test.sql#L220-L275) proves that an exact acceptance retry returns revision 2, leaves one applied revision, propagates the accepted epoch only to later unstarted targets, and rejects a second older proposal with `PT409 progression source changed`. That SQL file passed in the clean-stack run ([`pgtap.log`](../../work/clean-stack/posture-ai-strength-clean-release2-20260909/proof/pgtap.log#L40)).
- [`persistedProposal.test.ts`](../../lib/training/progression/persistedProposal.test.ts#L351-L393) proves an accepted target is not proposed again and a corrected actual produces a newly derived proposal. [`progression-proposals.test.ts`](../../lib/training/persistence/progression-proposals.test.ts#L402-L461) only reuses a proposal-key collision when every immutable stored binding matches.
- The retained pre-clean-stack two-connection result [`training-51000-races.log`](/Users/zero-suminc./.claude/goal-state/posture-ai-strength-conditioning/proof/training-51000-races.log) reports both `target_start` and `source_correction` races passed against [`training_revision_locking_race.mjs`](../../work/clean-stack/posture-ai-strength-clean-release2-20260909/supabase/tests/training_revision_locking_race.mjs). This supports serialization against a target starting or evidence being corrected during acceptance, but it is not part of the clean-stack execution.

No additional code is required for this criterion. If a single self-contained release artifact is required, rerun the unchanged two-connection race script against the final staged migration set and attach its output to the final release proof; the clean-stack receipt explicitly records that race scripts were not rerun.

## PR-14 — proven at the software authority boundary

**Criterion.** An athlete cannot publish a coach-owned target, and a routine coach override cannot clear an acute stop. Only the appropriately scoped actor may change a prescription or clearance.

The implementation fails closed at both application and database boundaries:

- [`authorization.ts`](../../lib/training/access/authorization.ts#L103-L123) grants athletes `program:self_publish`, coaches `program:coach_publish`, and grants neither actor `eligibility:clear`. [`authorization.test.ts`](../../lib/training/access/authorization.test.ts#L115-L125) and [`authorization.test.ts`](../../lib/training/access/authorization.test.ts#L222-L235) exercise those denials.
- The clean snapshot’s publish RPC requires the draft creator to be the current actor and requires either subject ownership for `self_directed` or the exact owning practitioner plus `program:coach_publish` for `coach_assigned` ([`20260907042000_training_program_sessions.sql`](../../work/clean-stack/posture-ai-strength-clean-release2-20260909/supabase/migrations/20260907042000_training_program_sessions.sql#L309-L338)).
- A subject owner cannot accept a coach-assigned exercise swap ([`training_exercise_swaps_test.sql`](../../work/clean-stack/posture-ai-strength-clean-release2-20260909/supabase/tests/training_exercise_swaps_test.sql#L467-L485)); the same athlete/owning-coach split is asserted for easier and harder recalibration ([`training_active_calibration_test.sql`](../../work/clean-stack/posture-ai-strength-clean-release2-20260909/supabase/tests/training_active_calibration_test.sql#L310-L321), [`training_manual_recalibration_test.sql`](../../work/clean-stack/posture-ai-strength-clean-release2-20260909/supabase/tests/training_manual_recalibration_test.sql#L366-L377)). All three files passed in the clean-stack SQL run ([`pgtap.log`](../../work/clean-stack/posture-ai-strength-clean-release2-20260909/proof/pgtap.log#L9), [`pgtap.log`](../../work/clean-stack/posture-ai-strength-clean-release2-20260909/proof/pgtap.log#L28), [`pgtap.log`](../../work/clean-stack/posture-ai-strength-clean-release2-20260909/proof/pgtap.log#L32)).
- The database coach-permission enum does not contain an eligibility-clearance capability ([`20260907041000_training_profiles_relationships.sql`](../../work/clean-stack/posture-ai-strength-clean-release2-20260909/supabase/migrations/20260907041000_training_profiles_relationships.sql#L433-L455)); attempting to store `eligibility:clear` is rejected ([`training_profiles_relationships_test.sql`](../../work/clean-stack/posture-ai-strength-clean-release2-20260909/supabase/tests/training_profiles_relationships_test.sql#L981-L996)). Authenticated clients cannot record authoritative eligibility decisions and coaches cannot submit athlete answers ([same test](../../work/clean-stack/posture-ai-strength-clean-release2-20260909/supabase/tests/training_profiles_relationships_test.sql#L605-L630)).

The former direct-evidence gap is closed by the post-clean-stack targeted proof in [`work/proof/pr14-authority-eligibility/manifest.json`](../../work/proof/pr14-authority-eligibility/manifest.json). [`training_live_program_build_source_test.sql`](../../supabase/tests/training_live_program_build_source_test.sql) passed 40/40 assertions with rollback, including a subject-owner athlete denied when publishing a coach-authored `coach_assigned` draft and an exact no-partial-assignment check. [`training_progression_proposals_test.sql`](../../supabase/tests/training_progression_proposals_test.sql) passed 22/22 assertions with rollback, including:

- an authoritative `acute_stop` superseding the previously supported decision;
- a `program:coach_publish` coach denied by the authoritative decision writer when attempting to clear that stop, with the acute-stop pointer unchanged;
- session start and progression acceptance denied after the acute stop, with the session, active program revision, prescription table, and acceptance table unchanged; and
- no boolean acknowledgement overload on either database mutation boundary.

Both targeted fixtures left zero matching rows after rollback. These 62 assertions were run against the retained local 69500-era schema after the clean-stack proof, so they extend rather than rewrite the earlier 45-file / 1,058-assertion record. No production function or permission was changed. PR-14 is therefore proven for the implemented software boundaries; this does not claim a clinical policy can clear an acute stop.

## EL-01 — partial; input gates exist, reviewed decision policy is missing

**Criterion.** Minor or unknown adult scope and unsupported requests deny assignment/start; a reviewed policy resolves the remaining answer combinations and constraints; pregnancy/postpartum context alone is neither a blanket denial nor clearance; acute stop has no acknowledgement bypass.

Implemented and evidenced behavior:

- [`eligibility.ts`](../../lib/training/contracts/eligibility.ts#L49-L70) strictly captures adult scope, activity, known disease categories, signs/symptoms, intended intensity, certainty, pregnancy/postpartum context, and requested scope. Its non-clinical gate denies minor/unknown adult scope, unsupported/unknown programming scope, and incomplete/uncertain answers ([`eligibility.ts`](../../lib/training/contracts/eligibility.ts#L242-L275)). [`eligibility.test.ts`](../../lib/training/contracts/eligibility.test.ts#L94-L151) proves those branches and proves pregnancy and postpartum are preserved with the same unavailable result rather than being interpreted as either a ban or clearance.
- The database preserves pregnancy context without creating a decision ([`training_profiles_relationships_test.sql`](../../work/clean-stack/posture-ai-strength-clean-release2-20260909/supabase/tests/training_profiles_relationships_test.sql#L284-L344)), rejects decision-shaped fields inside athlete answers ([same test](../../work/clean-stack/posture-ai-strength-clean-release2-20260909/supabase/tests/training_profiles_relationships_test.sql#L514-L520)), and rejects client-authored authoritative decisions ([same test](../../work/clean-stack/posture-ai-strength-clean-release2-20260909/supabase/tests/training_profiles_relationships_test.sql#L619-L630)). The file passed in the clean-stack run ([`pgtap.log`](../../work/clean-stack/posture-ai-strength-clean-release2-20260909/proof/pgtap.log#L37)).
- Live build, publish, and start are available only for a current, non-superseded `eligible_general` / `supported` decision tied to the latest athlete self-report, a confirmed adult scope, a supported request, and policy-service or qualified-reviewer provenance ([`20260907048000_training_live_program_build_source.sql`](../../work/clean-stack/posture-ai-strength-clean-release2-20260909/supabase/migrations/20260907048000_training_live_program_build_source.sql#L43-L97), [same migration](../../work/clean-stack/posture-ai-strength-clean-release2-20260909/supabase/migrations/20260907048000_training_live_program_build_source.sql#L305-L373)). A new symptom-bearing answer invalidates the earlier decision before publication and leaves no partial assignment ([`training_live_program_build_source_test.sql`](../../work/clean-stack/posture-ai-strength-clean-release2-20260909/supabase/tests/training_live_program_build_source_test.sql#L651-L693)); that file passed in the clean-stack run ([`pgtap.log`](../../work/clean-stack/posture-ai-strength-clean-release2-20260909/proof/pgtap.log#L31)).
- Acute stop precedes performance progression and returns a stop decision ([`decision.ts`](../../lib/training/progression/decision.ts#L158-L165), [`decision.test.ts`](../../lib/training/progression/decision.test.ts#L587-L594)). Neither the application action sets nor database relationship permissions expose a clearance override, as noted under PR-14.

The criterion is not complete. `gateEligibilityAnswersForAssignment` intentionally returns `eligibility_policy_unvalidated` even for complete, otherwise supported answers; it does not map disease/activity/intensity or fresh-symptom combinations to reviewed states. `cleared_with_constraints` likewise requires qualified-reviewer provenance while its constraint vocabulary remains explicitly unavailable ([`eligibility.ts`](../../lib/training/contracts/eligibility.ts#L131-L169)). Therefore the required “reviewed policy returns the remaining state/constraints” behavior does not exist, and this note does not claim clinical review or approval.

Completion needs two separate inputs:

1. **External clinical/human prerequisite:** approve a versioned policy decision table and constraint vocabulary for the named combinations, including pregnancy/postpartum handling. Software must not invent these outcomes.
2. **Software after approval:** implement the policy-service adapter that consumes an immutable answer revision and records the exact approved decision/provenance; add exhaustive pure decision-table tests and database/API scenarios showing minor, unknown, unsupported, fresh-symptom, and acute-stop cases deny build/publish/start with no partial writes, while each approved remaining state and constraint round-trips exactly.
